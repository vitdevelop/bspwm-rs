# bsp-compositor

The only crate that uses Smithay: it turns Wayland and hardware activity into `bsp-core` events and applies the effects the core returns. Builds the `bspwm-rs` binary.

## Nested compositor progress

Delivered and actually run inside a live Wayland session (Hyprland, nested — `docs/design.md` roadmap, the nested compositor: "winit backend, xdg-shell, tiling through the core, focus, borders"): the winit backend opens a real window, exposes a Wayland socket, and a real client (`alacritty`) connecting to it gets mapped as a `bsp-core` client node, tiled (arranged, sized via `xdg_toplevel`'s `configure`), focused, bordered, and cleanly unmapped on exit. Confirmed via `tracing` logs (`mapped a new window window=0x80000000 rect=Rect { x: 6, y: 6, width: 924, height: 1020 }` / `unmapped a window`) and the process staying stable afterward.

**`bsp-ipc`'s control socket is wired in and confirmed against the same live client**: `bspc-rs query -M --names`, `wm -g`, `query -T` and `node -t floating`/`node -t tiled` all round-tripped correctly against the running compositor — including `query -T`'s JSON showing the real `className`/`instanceName` ("Alacritty") picked up from `app_id_changed`, and the floating/tiled state transition actually resizing and repositioning the live window on screen via `shell::sync_wayland_from_core`. This — and the mapping/unmapping above — is the closest thing to an automated test this crate can have without a virtual display in CI: `WindowAdapter` and every `XdgShellHandler`/`CompositorHandler` impl need a live `smithay::desktop::Window`, which needs a real `ToplevelSurface`, which needs a running Wayland client.

One bspwm behavior gap found and fixed by this live testing: bspwm seeds a new client's `floating_rectangle` from its real on-screen geometry at map time (`src/window.c` `initialize_floating_rectangle()`, an `xcb_get_geometry` call before the window is tiled) — no Wayland equivalent exists, since an xdg-shell client has no on-screen geometry before its first `configure`. `map_new_toplevel` seeds it from the tiled slot just computed instead; without this, `bspc node -t floating` collapsed the window to 0×0 (clamped to 1×1) instead of keeping its size.

**`bspc rule` matching is now wired into window mapping**, live-verified against a real client: `map_new_toplevel` used to run unconditionally at `new_toplevel` time (the moment the `xdg_toplevel` role is created), before a client's `app_id`/title are guaranteed to have arrived — bspwm has no equivalent gap, since `apply_rules()` reads `WM_CLASS` with a synchronous `xcb_icccm_get_wm_class_reply()` call before the window is ever mapped (`src/window.c` `manage_window()`). Mapping is now deferred to the toplevel's first `commit` (`State::pending_toplevels`, `shell::on_commit`), by which point `set_app_id`/`set_title` have reliably run, and `bsp_core::rules::match_rules` (bspwm: `apply_rules()`'s full matching-and-merging loop, including its one-shot-stops-the-loop quirk) runs against the real `app_id`/title. The matched `RuleConsequence`'s `split_dir`/`split_ratio` (via presel on the insertion anchor), `layer`, `state`, `hidden`, `sticky`, `private`, `locked`, `marked`, `border` and `focus` are all applied. Confirmed live: `bspc rule -a "Alacritty:*:*" -o "state=floating sticky=on"` followed by launching `alacritty` produced a node with `"state":"floating"`, `"sticky":true` and a correctly seeded (non-zero) `floatingRectangle` on its very first frame, and `bspc rule -l` showed the rule gone afterward (one-shot).

Fixing the timing also surfaced and fixed a second, independent bug while testing with two windows at once: `map_new_toplevel` always passed `None` as `Tree::insert_node`'s anchor, which only behaves like "insert at the desktop's focus" when the tree is empty or has exactly one leaf — with two or more existing leaves it anchors at the tree *root* (an internal split node), not the focused leaf. Fixed to pass the desktop's actual `tree.focus`, matching bspwm's `manage_window()` (`f = mon->desk->focus`). Confirmed live: two `alacritty` windows now split side by side (`x: 6, width: 938` / `x: 952, width: 938`), not stacked or overlapping.

A related `RuleConsequence` correctness fix, needed to compute `should_manage`/`should_focus`/`should_border` at all: bspwm's `manage`/`focus`/`border` default to `true` (`make_rule_consequence()`, `src/rule.c`), with a rule only ever able to turn them *off* — but this crate's `RuleConsequence` originally modeled them as plain `bool`s defaulting to `false` via `derive(Default)`, meaning a rule that never mentioned `manage`/`focus`/`border` at all would (wrongly) compute as "don't manage, don't focus, don't border". Fixed by making all three `Option<bool>` (`docs/bsp-core.md`), matching `hidden`/`sticky`/`private`/`locked`/`marked`, which were already modeled that way.

Deliberately out of scope for this pass, each documented at its own call site with a `docs/bsp-compositor.md` Nested compositor scope reference rather than silently approximated:

- **`rule --add`'s `monitor=`/`desktop=`/`node=`/`rectangle=` targeting is applied** (`shell::map_new_window`, `bsp_ipc::exec::resolve_rule_target`): the node, else the desktop (at its focus), else the monitor (at its shown desktop) a matched rule names is where the window is inserted, as in bspwm's `manage_window()`; a sticky window ignores them. A window placed on a desktop that is not shown stays out of the space until that desktop is shown, and takes focus only through `follow=on` (`activate_node()` otherwise). `rectangle=` sets the floating rectangle. `honor_size_hints=` is parsed and shown by `rule --list` but not applied (no size hints are tracked).
- **`manage=false`**: parsed and merged into the resolved consequence (`RuleConsequence::should_manage`), but not applied — every window is still managed. bspwm's `manage=false` maps the X11 window exactly where the client itself put it, with no WM involvement (`src/window.c` `manage_window()`'s `!csq->manage` branch calling only `window_show()`); xdg-shell has no client-controlled position to fall back on, so honoring this needs its own placement-policy decision rather than an improvised default (hard rule 7 — stopped and asked before inventing one; not yet answered).
- **`center`/`follow`**: parsed and merged, but not applied. `center` needs floating-rectangle centering math with no `bsp-core` port yet (`docs/bsp-ipc.md`'s `node --move`/`--resize` gap is the same missing piece); `follow` only matters once `monitor=`/`desktop=`/`node=` targeting (above) can actually send a window somewhere other than the desktop it would have landed on anyway.
- **The emergency keys** `docs/design.md`'s Reliability section promises (Ctrl+Alt+F1–F12, Ctrl+Alt+Shift+Escape) are not implemented: they need their own hardcoded, sxhkdrc-independent path so a broken config can't disable them, not just a `bsp-hotkeys` binding — see Hotkeys and config progress below for what *is* wired in.
- **`bspwmrc`**: not read or run at startup.
- **`subscribe`'s events over the socket**: `Subscribers::broadcast_event`/`broadcast_report` are wired to fire after every executed command, but this has not yet been exercised with a live `bspc-rs subscribe` client (only request/reply commands have been live-tested so far).
- **`quit`'s exit status**: `bspc-rs quit <n>` stops the compositor but `<n>` is not threaded through to the process's own exit code yet.
- **Popup grabs**: a popup positions and shows correctly but cannot yet take an implicit pointer/keyboard grab that dismisses it on an outside click (`XdgShellHandler::grab` is a no-op).
- **xdg-decoration**: not offered as a global yet, so a client that insists on server-side decoration has no way to ask for it (most clients fall back to their own CSD, or none, without it).
- **Move/resize via pointer drag**: bspwm is a tiling WM and does not support this either (outside `state=floating`), so it is not a gap relative to bspwm, but noted since Smithay's `XdgShellHandler::move_request`/`resize_request` are left at their no-op defaults. `bspc node -v/-z` (programmatic move/resize) is also still unimplemented in `bsp-ipc::exec` itself (`docs/bsp-ipc.md`).
- **LED state, tablet, touch, gestures, relative pointer, pointer constraints, data device (clipboard), fractional scale, presentation-time**: no globals for any of these yet; a client that needs one simply does not see it advertised.

## Hotkeys and config progress

**`bsp-hotkeys` is wired in and live-verified** (`crate::hotkeys`): sxhkdrc is read at startup (`bsp_hotkeys::config::resolve_path`/`load`), and every keyboard event goes through `bsp_hotkeys::matcher::Matcher::feed` (`hotkeys::filter`, installed as `KeyboardHandle::input`'s filter closure) before it would otherwise reach the focused client — a completed chain dispatches either inline (`Dispatch::InlineBspc`, straight into `bsp_ipc::command::parse` then the same `ipc::execute_and_broadcast` the control socket itself calls) or as a spawned `sh -c` (`Dispatch::Shell`). Confirmed live against a running compositor and a real `alacritty` client, injecting genuine keyboard events via a `uinput` virtual device (host-level `wtype`/`ydotool`/`xdotool` were unavailable) targeting all three of: a `Dispatch::Shell` binding (a `touch` command, confirmed via the file appearing), a `Dispatch::InlineBspc` binding (`bspc node -c`, confirmed via `query -N` going empty), and a chord using an explicit `shift` modifier (confirmed via `bspc rule -l` showing the rule it added).

That live test caught and fixed two real bugs, neither in `bsp-hotkeys` itself (its own 64 unit tests, several exercising `shift`-modified chords against real `xkbcommon` keysym resolution, passed throughout — see `docs/bsp-hotkeys.md`'s Hotkeys and config progress for the detail on both):

- `Dispatch::InlineBspc`'s tokens start with the literal word `bspc`; `hotkeys::run_inline` was passing them to `bsp_ipc::command::parse` unstripped, which only expects the arguments *after* that (the real `bspc` binary strips its own `argv[0]` before putting a request on the wire). Fixed by skipping `tokens[0]`.
- `hotkeys::filter` matched a chord's keysym against Smithay's shift-*resolved* symbol (`KeysymHandle::modified_sym()`), so a config line like `super + shift + a` could never match: holding Shift turns the incoming symbol into `A`, and nothing parsed from the literal chord text `a` would ever equal that. Fixed by matching on `KeysymHandle::raw_syms()`'s level-0 (unshifted) symbol instead, letting the live `ModifiersState` and that fixed base symbol act as two independent conditions — exactly how bspwm's own `parse_event()`/`match_chord()` split the same problem (`src/sxhkd.c`/`src/types.c`).

**Full modifier coverage (`hyper`/`meta`/`mode_switch`/`mod1`..`mod5`, alongside the already-working `shift`/`control`/`lock`/`alt`/`super`) is implemented and live-verified** (`hotkeys::resolve_modifiers`/`canonicalize_virtual_modifiers`/`real_bit_for`, `docs/design.md`'s Hotkeys and config row). Split across two mechanisms, for two different reasons:

- `resolve_modifiers` reads `Mod1`..`Mod5` straight off the *fields* Smithay's own `ModifiersState::update_with` already computes (`smithay-0.7.0/src/input/keyboard/modifiers_state.rs`: `xkb::MOD_NAME_ALT`/`_NUM`/`_MOD3`/`_LOGO`/`_ISO_LEVEL3_SHIFT` are literally the strings `"Mod1"`..`"Mod5"`), so it only ever populates the held set with the real modifiers Shift, Control and Mod1, Mod3, Mod4, Mod5 — never Caps Lock or Num Lock (sxhkd masks its `lockfield` off before matching, `src/sxhkd.c`, so hotkeys work whatever their state) and never `Alt`/`Super`/`ModeSwitch`/`Hyper`/`Meta` — `bsp_hotkeys::binding::Modifier::canonical` (`docs/bsp-hotkeys.md`) is what lets a chord still written `alt`/`super`/`mode_switch` match that real-bit-only set.
- `hyper`/`meta` have no fixed real-bit alias the way `alt`/`super`/`mode_switch` do — which real bit (if any) a keymap backs them with is a genuinely dynamic, keymap-dependent property (the Wayland/xkbcommon equivalent of sxhkd's own `modfield_from_keysym(Hyper_L)`/`modfield_from_keysym(Meta_L)`, `src/parse.c` `parse_modifier()`), so `canonicalize_virtual_modifiers` resolves it once, when sxhkdrc is (re)loaded, rewriting a loaded chord's `Hyper`/`Meta` modifiers to whichever real bit `real_bit_for` finds — not per key event, since key events are a much hotter path than a config (re)load. `crate::pointer_action::canonicalize_modifier` reuses the same `real_bit_for` for `pointer_modifier hyper`/`meta`, resolved per press instead (a single value, not a whole chord list to rewrite in place, and `cleaned_modifiers` already pays for one `with_xkb_state` call on every press regardless).

`real_bit_for` itself can't just compare modifier *indices*: unlike a real modifier, a virtual one (`Hyper`/`Meta`) gets its own, entirely separate index into the keymap's modifier table (`Keymap::mod_get_index`) — never equal to any real modifier's fixed index 0..8, even where holding that real modifier *does* activate the virtual one at runtime (confirmed live: this environment's default keymap resolves `"Meta"` to index 13, `"Mod1"` to index 3, yet holding physical Alt activates both). `libxkbcommon` has no direct query for "which real bit does virtual modifier X depend on", so `real_bit_for` probes for the answer empirically instead: build one throwaway `xkb::State` from the same `Keymap`, assert each real modifier alone in turn (`State::update_mask`), and check whether that alone activated the named virtual modifier (`State::mod_index_is_active`) — the same computation `mod_name_is_active` performs against the live state, just run once per real modifier against a synthetic one.

A first attempt at `hyper`/`meta` support queried `mod_name_is_active("Hyper"/"Meta", ...)` directly against the *live* state on every key event, the same way `resolve_modifiers` handles the other six modifiers, inserting `Modifier::Hyper`/`Meta` into the held set alongside whatever real bit was also active. Live-testing caught a real bug this introduced: on this environment's (and, per `xkbcli compile-keymap`'s stock `pc` ruleset output, essentially every default Linux keymap's) `modifier_map Mod1 { <LALT>, <RALT>, <ALT>, <META> }`, physical Alt activates the virtual `Meta` modifier too — so the held set became `{Mod1, Meta}` while an existing, previously-working `alt + x` chord's modifiers canonicalize to just `{Mod1}`; `bsp_hotkeys::matcher::modifiers_match`'s exact-set comparison (a real bspwm quirk, reproduced deliberately, not smoothed over) correctly judged that a mismatch and silently broke a binding that had nothing to do with `meta` at all. Real sxhkd never hits this, since `modfield_from_keysym` resolves a modifier name to a bit *once*, at parse time — its `modfield` bitmask has no way to carry an "extra" bit a chord's own text never named. `canonicalize_virtual_modifiers` restores that same one-time-resolution property instead of tracking `hyper`/`meta` as live, independently-held state, which is what fixed it.

Confirmed live against a running compositor and a real `uinput` keyboard: a chord written `mod1 + minus` fired while holding physical Alt (proving `Mod1` resolution and, since this keymap's Alt also asserts `Meta`, proving the fix for the bug above in the same test); a plain `alt + minus` chord still fired afterward (confirming no regression); and a chord written `meta + minus` fired too (confirming `canonicalize_virtual_modifiers`'s dynamic `Hyper`/`Meta` resolution). `bspc config pointer_modifier meta` was confirmed to round-trip (`get` echoes back the literal `meta` the user set, not a canonicalized form — `canonicalize_modifier` only resolves it at comparison time, inside `on_button_press`).

**Pointer bindings (`bspc config pointer_modifier`/`pointer_action1..3`/`click_to_focus`/`pointer_motion_interval`/`swallow_first_click`) are wired in and live-verified** (`crate::pointer_action`, `docs/bsp-hotkeys.md`'s "Pointer bindings for moving and resizing floating windows, as bspwm's `pointer_action` settings do"). Ported from bspwm 0.9.12's actual `src/pointer.c`/`src/events.c`/`src/settings.c`/`src/window.c` source — cloned and read directly rather than recalled, since several details are easy to get wrong from memory alone (confirmed by finding two of them: `get_handle()`'s `ACTION_RESIZE_SIDE` case splits the rectangle along both diagonals, not "nearest edge by distance"; `move_client()`'s tiled branch is a live drag-to-swap with whatever tiled leaf is currently under the pointer, not an implicit float-then-move).

- **The X11-passive-grab-to-Wayland translation**: bspwm registers one X11 passive button grab per `click_to_focus` button (no modifier) and one per button with a configured `pointer_action` (held with `pointer_modifier`) — `window_grab_buttons()` — so `button_press()` only ever runs for a press one of those two grabs already selected, and its `cleaned_mask` check just disambiguates which. Wayland has no passive-grab equivalent (this compositor sees every press unconditionally), so `pointer_action::on_button_press` re-derives that same selection itself: a press matching neither a plain `click_to_focus` button nor `pointer_modifier`+a configured action is forwarded to the client completely untouched — exactly as if bspwm had never registered a grab for it either. This needed correcting a *pre-existing* Nested compositor behavior: `input::on_pointer_button` previously focused on *every* click unconditionally (more permissive than bspwm's own `click_to_focus` default), a real, if minor, deviation fixed as part of this pass, not left in place.
- **`pointer_modifier`'s vocabulary**: stored as `bsp_hotkeys::binding::Modifier` (default `Super`, `binding::Modifier::parse` made `pub` for this reuse) rather than bspwm's literal `mod1`..`mod5`/`shift`/`control`/`lock`-only vocabulary (`parse_modifier_mask()`) — every one of those raw bit names is fully supported too (`cleaned_modifiers` resolves `Mod1`..`Mod5` from the live keymap, full modifier coverage, this doc's own Hotkeys and config progress above), this crate's vocabulary is simply a deliberate superset: it also accepts `hyper`/`meta`/`mode_switch`, which `parse_modifier_mask()` itself does not, the same wider grammar `bsp-hotkeys` already parses for sxhkdrc chords. A deliberate, documented deviation from the wire vocabulary, not a guess; `pointer_action1..3`/`click_to_focus`'s own vocabulary (`move`/`resize_side`/`resize_corner`/`focus`/`none`, `any`/`buttonN`/`none`) matches bspwm's exactly, since those map cleanly.
- **The interactive drag itself**: a [`smithay::input::pointer::PointerGrab`] (`pointer_action::DragGrab`), Smithay's own mechanism for exactly this (anvil and every other Smithay compositor's move/resize use the same trait) — the Wayland equivalent of `track_pointer()`'s blocking X11 event loop. Set with `Focus::Clear` on `begin_action`, so the dragged/resized client receives no pointer motion at all while the compositor drives it, matching bspwm's fully-swallowed X11 grab. `PointerAction::Move` on a `Floating`/`Fullscreen` node calls `Tree::move_floating` per motion tick (throttled by `pointer_motion_interval`, exactly like bspwm's own `dtime < pointer_motion_interval` check); on a `Tiled`/`PseudoTiled` node it re-queries whatever window is now under the pointer (`state.space.element_under`) and calls `Tree::swap_nodes` when it's a different tiled leaf on the same monitor, then re-arranges and re-syncs — `bsp_core::tree::Tree::swap_nodes` is structural only (`docs/bsp-core.md`: bspwm's own C `swap_nodes` also carries the X11 side effect of moving the real windows; this port doesn't), so doing that explicitly here is this caller's job. `PointerAction::ResizeSide`/`ResizeCorner` compute a `ResizeHandle` once at grab start (`Tree::get_handle`, not recomputed per tick, matching `track_pointer()`) and feed each tick's delta to `Tree::resize_node`.
- Confirmed live against a running compositor with two real `alacritty` clients (via the same `uinput` virtual-device method as the rest of Hotkeys and config): `pointer_modifier`+button1 dragged a floating window by the exact delta; `pointer_modifier`+button3 (`resize_corner`, the default) grew a floating window's rectangle correctly from the dragged corner; `pointer_modifier`+button1 dragged one tiled window into another's screen area and the two swapped tiled positions (confirmed via their on-screen rectangles), re-arranging live; every `bspc config` get/set/invalid-value round trip for all five settings.
- **A real bug found and fixed by this live testing**: `pointer_action::on_button_press` is plain application logic called before `PointerHandle::button()`, not part of Smithay's own grab dispatch — without an explicit `state.pointer.is_grabbed()` check, a second button pressed mid-drag could start a second, overlapping grab on top of the first (bspwm's own X11 grab has no such hazard, since its passive-grab mask only ever listens for `BUTTON_RELEASE`/`MOTION` while active, never a second press).

`focus_follows_pointer` (`input::focus_follows_pointer`, called after every pointer motion) focuses the managed window the pointer moved onto, or the monitor under it over empty space; not during a drag, under a lock, or while a panel has the pointer. `pointer_follows_focus`/`pointer_follows_monitor` (`input::warp_pointer_for_focus`) move the pointer to the centre of the newly focused window or monitor after a `bspc` command or hotkey changed the focus (not after a click or a new window, where bspwm would warp too). `swallow_first_click` is honoured: a click that moved focus reaches the client unless it is on, and a swallowed press's release is swallowed with it (`State::swallowed_buttons`). Still not implemented: `grab_pointer()`'s "click on empty monitor background switches monitor focus" case and cross-monitor transfer on a floating drag.

**`bspc config hotkeys_inline_bspc` is wired in and live-verified** (`docs/bsp-hotkeys.md`'s "Binding execution" off switch). `State::hotkeys_inline_bspc` is a compositor-local `bool` (default `true`) rather than a `bsp_core::wm::Wm::settings` field — `bsp-core::Settings`' own module doc comment deliberately reserves settings that only matter to `bsp-compositor` (`docs/bsp-core.md`), and this one has nothing to do with the tree engine at all. `ipc::try_hotkeys_inline_bspc` intercepts a `Command::Config` naming this exact setting before it would otherwise reach `bsp_ipc::exec::execute` (which has never heard of it and would reply with its generic "Unknown setting" fallback), handling get and set directly against `state.hotkeys_inline_bspc` with the same `bool`/`Reply` conventions `bsp_ipc::exec`'s own settings use. Called from both `ipc::on_readable` (the socket path) and `hotkeys::run_inline` (the in-process hotkey path), so a hotkey bound to this exact command behaves identically either way — the same equivalence construction as `ipc::execute_and_broadcast` itself. `hotkeys::run`'s dispatcher checks the flag before honoring a `Dispatch::InlineBspc` classification: when `false`, every binding — including one classified as `InlineBspc` — runs through `run_shell` instead, using `LoadedHotkey::command`'s verbatim text (`docs/bsp-hotkeys.md`) rather than re-joining `InlineBspc`'s already-split tokens. Confirmed live: over the socket, the default read back as `true`, a set/get round-tripped, and an invalid value was rejected; via real key presses (a `uinput` virtual keyboard against a running compositor, same method as the rest of Hotkeys and config), a hotkey bound to `bspc config border_width 7` changed `border_width` in-process with the flag `true`, and left it unchanged with the flag `false` (the shell fallback's `sh -c "bspc config border_width 7"` fails silently — no real `bspc` binary on `PATH` in this environment — which is exactly the distinguishing, observable effect the off switch is supposed to have).

**`bspc wm -r` is wired in and live-verified as a live reload, not a process restart** (`ipc::execute_and_broadcast`, `docs/design.md` Compatibility: "restarting a Wayland compositor kills every client"). `bsp_ipc::exec::exec_wm` already produces the right `Reply` for `WmAction::Restart` (`Reply::Ok`, no `Event`s, and it stops processing any further `wm` actions in the same command — bspwm: `src/messages.c` `cmd_wm()`) but performing an actual restart is a compositor-only side effect `bsp-ipc` has no way to do itself, so `execute_and_broadcast` inspects the original `Command` after running it: if it was `Command::Wm` naming `WmAction::Restart` and the reply was `Reply::Ok`, it also calls `bspwmrc::run()` and `hotkeys::reload` — re-running `bspwmrc` and re-reading sxhkdrc, exactly `SIGUSR1`'s reload plus one extra step, without touching any mapped client or `bsp-core` state. Wired into the same shared function the control socket and `hotkeys::run_inline` both already call, so a hotkey bound to `bspc wm -r` behaves identically to the socket path. Confirmed live: `bspc-rs wm -r` re-ran a test `bspwmrc` (its marker file gained a second line) and re-read a changed sxhkdrc (the *new* binding fired on the next key press, not the old one) while the compositor and its one existing monitor stayed up throughout; a hotkey bound to `bspc wm -r` produced the identical marker-file/reload effect.

**`SIGUSR1` reloads sxhkdrc and is live-verified** (`hotkeys::reload`, `docs/bsp-hotkeys.md`'s "Config reload on `SIGUSR1`, matching sxhkd"). Registered via `calloop::signals::Signals` (`smithay::reexports::calloop`'s own copy, gated behind calloop's own `signals` Cargo feature — turned on from this crate's `Cargo.toml` even though nothing here uses `calloop` directly otherwise, since `smithay`'s own dependency declaration doesn't enable it) right after the control socket starts listening. `reload` re-reads sxhkdrc from scratch and replaces `state.hotkeys`/`state.hotkey_matcher` outright, matching sxhkd's own `reload_cmd()` (`cleanup()` then `load_config()` again) — and, as a side effect of building a fresh `Matcher`, also resets any in-progress chain's `chained`/`locked` state, which sxhkd's own `cleanup()` leaves dangling if a chain happened to be mid-progress at reload time (a safe improvement over the reference behavior, not a deviation worth its own `docs/design.md` row, since it's invisible except in that edge case). Confirmed live: an initial sxhkdrc's binding fired, the file was replaced with a different binding, `SIGUSR1` was sent, and only the *new* binding fired afterward — the old one was confirmed gone, not just shadowed.

**The `Ctrl+Alt+Shift+Escape` emergency quit key is implemented and live-verified** (`input::is_emergency_quit`, `docs/design.md`'s Reliability section: it must work "independent of sxhkdrc"). Checked directly in `process_input_event`'s keyboard filter closure, before `hotkeys::filter` ever runs — a broken, missing, or maliciously-crafted sxhkdrc has no way to intercept or disable it, since it never goes through `bsp-hotkeys`' matcher at all. Confirmed live: sending the combo via a synthetic `uinput` keyboard against a running compositor (with no sxhkdrc loaded at all) made the process exit cleanly (`exited with code 0`) with no errors logged. `Ctrl+Alt+F1`–`F12` (TTY switch) is not applicable to the nested backend (no session to switch within); it is implemented on the DRM backend, see Hardware backend progress, Stage D.

**`bspwmrc` is run at startup and live-verified** (`crate::bspwmrc`, `src/bspwm.c` `main()`'s config-path resolution and `run_config()` call site, `src/settings.c`). Resolved from the same path real bspwm reads (`$XDG_CONFIG_HOME/bspwm/bspwmrc`, else `$HOME/.config/bspwm/bspwmrc` — deliberately not a `bspwm-rs`-specific path, `docs/migrating.md`), `execl`'d directly rather than through `sh -c` (it is expected to be its own executable script, shebang line and all — the same as bspwm), given one argument (the "run level", always `"0"` here since this build has neither `--load-state` nor an externally-provided socket fd to set bspwm's two bits), and not waited on, called right after the control socket starts listening — matching bspwm's own ordering, since `bspwmrc` typically issues `bspc` commands against it as it runs. Confirmed live: a test `bspwmrc` receiving `$1` and touching a marker file named after it produced `bspwmrc-ran-with-arg-0`; with no `bspwmrc` present at all, startup logs `"no bspwmrc found"` at `info` level and continues normally, no warning or error (`docs/design.md`'s Reliability section: a missing config must never lock the user out).

## Protocols progress

Protocols is a long list of protocols (`docs/design.md`); they are added in batches, each live-verified in the VM with real clients. Nothing here has a bspwm counterpart to cite — X11 provides these as built-ins (selections, RandR, struts), so each entry says what it replaces.

**Batch 1 — clipboard, primary selection, data-control, xdg-output (done).** `crate::protocols::Protocols` creates the `wl_data_device_manager` (clipboard and drag-and-drop), `zwp_primary_selection_device_manager_v1`, `zwlr_data_control_manager_v1` and `zxdg_output_manager_v1` globals; `SeatHandler::focus_changed` points the clipboard and primary selection at the client owning the newly focused surface (Wayland only shows a selection to the focused client; data-control lets `wl-copy`/`wl-paste` and clipboard managers bypass that). Live: `wl-copy`/`wl-paste` round-trip for both the clipboard (text types listed: `text/plain`, `UTF8_STRING`, …) and, with `--primary`, the primary selection, and a second `wl-copy` replaces the first. Not done: a drag icon is not drawn during drag-and-drop; `ext-data-control` (the newer standard twin of the wlr protocol) is not added; xdg-output is advertised but was not exercised by a client.

**Batch 2 — layer-shell (done).** Replaces `_NET_WM_STRUT`. `crate::layers` maps each layer surface onto an output's Smithay `LayerMap` (client's chosen output, else the focused monitor's, else the first), sends the initial configure on the first commit (Smithay's `arrange` deliberately never does; without it clients hang and the surface stays 0x0 — found by the live test: waybar logged "Timed out waiting for initial .configure"), and after every arrange turns the map's non-exclusive zone into `bsp_core::monitor::Monitor::struts` and re-tiles the monitor's desktops, so tiled windows sit below a bar (a test window's slot moved down by the bar's 30 px). Stacking, top to bottom: cursor, overlay, top, window borders, windows, bottom, background. Pointer hit-testing (`layers::surface_under`) checks overlay/top, then windows, then bottom/background, and a click on a layer surface that accepts keyboard focus (on-demand or exclusive) focuses it without click-to-focusing the window beneath; an exclusive top/overlay surface takes keyboard focus when it commits. Frame callbacks go to layer surfaces; layer surfaces are closed when their output disconnects; a mode/scale/position change re-arranges them. Live (DRM backend, two outputs): `swaybg` wallpaper and `waybar` (real modules: clock, network, caps/num-lock indicator) rendered on top of the layout with the tiled window below the bar. Not done: waybar-style popups on layer parents work only as far as xdg popups already do (no popup grab); layer surfaces moving between outputs on hotplug is not handled (they are closed).

**Batch 3 — xdg-output (worked on), xdg-activation, idle, foreign-toplevel-list, shortcuts-inhibit, virtual keyboard, cursor-shape, viewporter (all live-verified).**
- **xdg-output**, verified with a purpose-built client (`examples/protocol_probe.rs`, see below): per-output name, logical position and size, and description. Fixes/additions: the description is now the monitor's real identity — `crate::edid` parses the connector's EDID blob by hand (`smithay-drm-extras`' own EDID support needs a `libdisplay-info` version this system's does not satisfy) into make (three-letter PnP id) and model, so the QEMU monitors read `RHT - QEMU Monitor - Virtual-1`. Live: `bspc output Virtual-1 -s 2 -p 100 50 -m 1024x768` immediately changed the reported logical position to `100,50` and size to `512x384` (1024×768 at scale 2), the other output untouched. Not done: no `done`-batched rename events (names never change).
- **xdg-activation** (`_NET_ACTIVE_WINDOW`'s analogue): a token is only issued if the request carries an input serial; a request with a token under 10 s old for a mapped window focuses it (moving to its desktop/monitor, like bspwm's `focus_node`); tokens are one-shot. **Live-verified**: a background window asked for activation with its keyboard-enter serial while a second window had focus — `bspc query -N -n focused` went from the second window's node to the first's and the first got `keyboard enter` again.
- **Idle** (`ext-idle-notify`, `idle-inhibit`): every input event (winit and libinput) counts as activity; an inhibiting surface suspends idle notifications. **Live-verified**: with a 3 s timeout the probe got `idled` after 3 s, `resumed` on the next pointer motion, `idled` again 3 s later; with an inhibiting window open no `idled` arrived, and 3 s after that window's client was killed `idled` did. That test found a real bug: Smithay calls `uninhibit` only when a client explicitly destroys its inhibitor, so an exited or crashed client inhibited idling forever — `protocols::refresh_idle_inhibit` now drops inhibitors of dead surfaces after each event-loop turn.
- **`ext-foreign-toplevel-list`** (identifier, title, app id, closed) is tracked from map/unmap and title/app-id changes; the probe listed the live test window (`es2gears`). The wlr taskbar protocol (`zwlr_foreign_toplevel_manager_v1`, what waybar's taskbar uses) is not in Smithay and is not implemented yet.
- **Shortcuts inhibit**: a granted inhibitor stops the sxhkdrc filter for the focused client; the emergency quit key and VT switching still work. **Live-verified** with a synthetic `Ctrl+Alt+P` binding (`touch` a marker file) injected through the QEMU monitor: it fires with an ordinary window focused and does not fire while a window holding an inhibitor is focused (that window logged `shortcuts inhibitor active`).
- **Virtual keyboard** (`wtype`, on-screen keyboards): advertised to every client for now — restricting it waits for security-context. **Live-verified**: a client re-uploaded the seat's keymap, typed `A` through `zwp_virtual_keyboard_v1`, and the focused window received `key 30 pressed`/`released`.
- **Cursor shape** now draws the requested cursor from the xcursor theme (cached per shape, falling back to the default arrow) and **viewporter** is advertised. **Live-verified** with a window that set `wp_cursor_shape` `crosshair` on pointer enter (a screendump shows the crosshair) and a 64×64 buffer with a `wp_viewport` destination equal to the configured size (the screendump shows it filling the whole window).
- **A `bsp-ipc` bug found by this testing**: `bspc query -N -n focused` listed every node instead of only the focused one (the `-n` selector was resolved but never applied in the `Nodes` domain) — fixed in `exec_query` (bspwm's `query_node_ids()` lists just the resolved node), with a unit test.
- **Test clients** (`cargo build -p bsp-compositor --examples`): `examples/protocol_probe.rs` (`globals`, `xdg-output`, `toplevels`, `idle MS`) and `examples/window_probe.rs` (maps a solid-colour window; `--inhibit-idle`, `--inhibit-shortcuts`, `--viewport`, `--cursor SHAPE`, `--activate-self-after SECS`, `--vkbd`), used in the VM where tools like `wayland-info` are missing.

**Batch 4 — the protocols Smithay does not provide (written here on the `wayland-protocols`/`wayland-protocols-wlr` server bindings).** All were tested in the VM with real clients (`waybar`, `wlr-randr`, `grim`) or the probe clients.
- **`wlr-foreign-toplevel-management`** (`crate::taskbar`): what taskbars and switchers use to show every window (title, app id, activated/minimized/fullscreen, output) and to focus, close, hide or fullscreen one — replacing EWMH's `_NET_CLIENT_LIST`/`_NET_WM_STATE`/`_NET_ACTIVE_WINDOW`. Requests are run as `bspc node` commands, so they share the code path of a hotkey or `bspc`. **Live**: waybar's `wlr/taskbar` listed both test windows.
- **`ext-workspace-v1`** (`crate::workspaces`): monitors are groups, `bsp-core` desktops are workspaces, the monitor's focused desktop is the active one; `activate` at `commit` is `bspc desktop ID -f`. **Live**: waybar's `ext/workspaces` showed `I`, then after `bspc monitor -a II; bspc desktop II -f` showed `II` as active, and back.
- **`wlr-virtual-pointer-v1`** (`crate::virtual_pointer`): absolute/relative motion, buttons, scroll frames, injected through `input::pointer_motion_to`/`deliver_button` (refactored out of the libinput path) so click-to-focus and pointer bindings see them. **Live**: a client received `pointer enter`, `motion`, and button 272 press/release from another client's virtual pointer.
- **`wlr-output-management`** (`crate::output_management`): `wlr-randr` lists both outputs with make/model, physical size, modes, position, scale; `--custom-mode 1024x768@60 --scale 2 --pos 100,50` changed the real output (the monitor rectangle became `100,50 512x384`) and reverting worked. Transforms (rotation and flips) are supported: `--transform 90`, `flipped` and `normal` were accepted in the VM and the monitor rectangle swapped to 800x1280 for 90 (pixels not inspected). Unsupported and reported as a failed configuration: turning an output off, adaptive sync. A configuration made against an outdated serial is `cancelled`. `wlr-randr --mode WxH@60Hz` needs the refresh to match a real mode exactly (60.004 ≠ 60), which is that tool's rule.
- **`wlr-screencopy`** (`crate::screencopy`): `grim` (whole layout, region `-g`, cursor `-c`) works; only shm buffers are offered. The DRM backend renders the output off-screen on the primary GPU's GLES renderer and copies it into the client's buffer. **Live**, pixel-checked: a red 64×64 test window at (6,6) appears at exactly x 6–69, y 6–69 of the captured 2560×800 image. That check found a real bug — captures were upside down (GL's bottom-left origin); the off-screen render now uses `Flipped180`. `copy_with_damage` is answered on the next rendered frame with the whole frame as damage.
- **`wlr-gamma-control`** (`crate::gamma`): implemented against the CRTC's `GAMMA_LUT`/`GAMMA_LUT_SIZE` properties (`drm-ffi` creates the runtime-sized blob). The QEMU virtual GPUs expose no LUT, so live it only shows the refusal path (`gamma failed`) — the ramp-writing path is **untested** until run on real hardware; debug logging (`writing the gamma LUT`, `gamma control granted/refused`) shows what happens there.
- **Two bugs from earlier work found while testing this batch**: (1) windows of a monitor's non-focused desktops stayed on screen, and their borders too — `desktop -f` never hid anything; `sync_wayland_from_core` and the border renderer now show only each monitor's focused desktop (bspwm `show_desktop`/`hide_desktop`); (2) the seat's keyboard focus did not follow `bsp-core`'s focus after `bspc desktop -f`/`node -f`/closing a window — `input::sync_keyboard_focus` now runs after every reconcile (a layer surface holding focus is left alone).

**Batch 5 — decorations, scaling, pointer capture, lock, sandboxing, presentation, input methods, more capture.** All tested in the VM with `window_probe`/`protocol_probe`, `grim` or `wlr-randr` unless noted.
- **`xdg-decoration`**: every toplevel is told *server-side* (bspwm draws only a border, no title bar). Live: a client that requested client-side was answered server-side.
- **`wp-fractional-scale`**: each window and layer surface is told its output's scale (also after `bspc output -s`). Live: `preferred scale 1.500`, then `2.000`.
- **`wp-single-pixel-buffer`**, **`wp-content-type`** (accepted only): Live: a single-pixel buffer scaled by a viewport drew exactly 200×200 pixels of its colour in a `grim` capture.
- **`pointer-constraints` / `relative-pointer`** (`crate::constraints`): a locked pointer stays put while the client still gets relative motion; a confined one cannot leave its surface; constraints activate on pointer focus and release when it leaves; `cursor_position_hint` moves only the compositor-side location while the lock is active (no `motion` event to the client, which would feed Xwayland's per-event hints back as motion). `constraints::relative_motion` is now the single relative-motion path (libinput and virtual pointers) — which also fixed the libinput path clamping the pointer to the *first output only*. A constraint's region is not honoured when activating. A lock counts only while its surface is still under the pointer (a switched-away desktop must not freeze it). A fullscreen X11 window that has an emulated video mode (`xwayland::emulated_size`) keeps that size at the output origin; Xwayland scales it. Live: a client locked the pointer, virtual relative motion arrived as `relative motion 30,20` while `pointer motion` stayed at the same position.
- **`ext-session-lock-v1`** (`crate::session_lock`): described in the module docs. Live: while a locker held the session 100% of a `grim` capture (both outputs) was the lock surface's colour and the red test window was gone; an `Ctrl+Alt+P` sxhkdrc binding was suppressed while locked and worked again after unlock; the lock is confirmed only once every output has a lock surface. A locker that dies leaves the session locked (as the protocol requires; the emergency quit key still works).
- **`wp-security-context-v1`** (`crate::state::is_privileged`): a socket created through it produces *sandboxed* clients that cannot see screen capture, virtual input, window lists, output management/power, gamma, session lock, layer shell, clipboard managers, input methods or security-context itself (custom globals implement `GlobalDispatch::can_view`; Smithay's take a filter). Live: a normal client saw 10 of 10 privileged globals, a client connected through the new socket saw 0 of 10 among 23 total.
- **`wp-presentation`**: the DRM backend queues each frame with the presentation feedback of the surfaces it shows and answers at vblank with the kernel's timestamp, sequence and the output refresh. Live: `presented seq=0 refresh=13334400 ns` (75 Hz). Feedback of empty (not queued) frames and of layer surfaces is not collected.
- **`wp-tearing-control-v1`** (`crate::tearing`): hint stored, presentation stays vsynced (Smithay's DRM path has no async flip). Live: the hint was accepted.
- **`text-input-v3` / `input-method-v2`**: served (input-method restricted to privileged clients; an engine's popup is tracked as a popup of the focused window). Live: both globals advertised and a client enabled a text input without errors; **no input method engine was available, so composition itself is untested**.
- **`ext-image-copy-capture-v1`** (`crate::ext_capture`): output sources only (no toplevel sources, no dmabuf, cursor sessions answer `stopped`). Live: a session reported 1280×800 and a captured frame arrived intact.
- **`wlr-output-power-management`** (`crate::output_power`): DPMS through the connector property. Live: `dpms` in sysfs went `On` → `Off` → `On` with the protocol's `mode` events; an off output is not rendered.
- **Portals**: the compositor exports `XDG_CURRENT_DESKTOP=bspwm-rs` and (when the login says `tty`) `XDG_SESSION_TYPE=wayland`; `contrib/portals/bspwm-rs-portals.conf` maps Screenshot/ScreenCast to `xdg-desktop-portal-wlr`. **Untested**: no portal daemons in the VM.

**Batch 6 — the rest of the list: capture buffers and sources, pacing, dialogs, drags, gestures, tablets (done).** Smithay provides `alpha-modifier`, `fifo`, `commit-timing`, `xdg-dialog`, `xdg-foreign`, `xdg-toplevel-icon`/`tag`, `xdg-system-bell`, `xwayland-keyboard-grab`, `pointer-gestures` and `tablet-manager` (`crate::extras`); the rest is written here on the `wayland-protocols(-wlr)` bindings. Tested in the VM with `window_probe` (new options `--modal --alpha --fifo --commit-timing --tag --icon --bell --export --drag --gestures --tablet`), the new `examples/capture_probe.rs` (DRM only) and input injected through QMP.
- **`wp-alpha-modifier`**: Smithay's surface render element applies it. Live: a `grim` capture of a red window read `(255,0,0)` opaque and `(138,10,10)` at 50 % over the `(20,20,20)` background.
- **`wp-fifo`**: a commit that waits on a barrier is held until a frame is presented; `extras::finish_frame` (both backends' end-of-frame) releases the barriers and then tells each client's compositor state the blocker cleared — **Smithay does not poll blockers**, without `blocker_cleared` the first frame worked and every later commit hung (found live). Live: four commits produced four frame callbacks on four separate frames.
- **`wp-commit-timing`**: a commit with a timestamp waits behind a barrier that only a frame end would release, and this compositor draws nothing while idle, so `extras::arm_commit_timers` (after each event-loop turn) arms one calloop timer for the earliest pending deadline; it releases the due commits and queues a frame. Live: a timestamp 800 ms ahead produced its frame callback at 809 ms. No commit-timed client, no timer.
- **`xdg-dialog`**: a modal toplevel is floated and centred (like an X11 dialog under bspwm's rules); set before the first commit it is honoured at map time, set later it runs `bspc node -t floating`. Live: the modal window's node reported `floating`, the other stayed `tiled`.
- **`xdg-foreign`** (handle export verified live), **`xdg-toplevel-icon`/`tag`** (accepted without error; bspwm draws no title bars or icons, so nothing shows them), **`xdg-system-bell`** (logged).
- **`xdg-toplevel-drag`** (`crate::toplevel_drag`): during a drag whose data source is wrapped by an `xdg_toplevel_drag_v1`, the attached toplevel is floated and moved to keep the pointer at the given offset (`Tree::move_floating`); it stays where it was dropped. Live, with a client that started the drag on a button press and a mouse moved through QMP: the window went from tiled `(6,6)` to floating `(315,237)`.
- **Capture into dmabufs and of single windows** (`crate::screencopy`, `crate::ext_capture`, `crate::export_dmabuf`): `Backend::capture_dmabuf_caps`/`capture_into_dmabuf`/`allocate_capture_buffer` render on the primary GPU straight into a client buffer (`linux_dmabuf` event of `wlr-screencopy` v3 for whole outputs; `dmabuf_device`/`dmabuf_format` of the ext session), a dmabuf being rendered with `Transform::Normal` (only the shm read-back needs `Flipped180`). The `ext-foreign-toplevel-image-capture-source` global adds toplevel sources: only that window's surfaces, sized to its geometry, whether or not it is covered. A resize is announced as new buffer constraints and the pending frame fails with `buffer_constraints`; a window that closed gives `stopped`. `wlr-export-dmabuf` sends the plane file descriptors of a private copy (the generated bindings can only mark it `transient`). Live, byte-compared with `capture_probe`: wlr dmabuf vs shm and ext dmabuf vs shm of the whole output matched, ext dmabuf vs shm of a toplevel matched, the exported dmabuf imported through GBM and held the picture, the resize and the close behaved as described.
- **Pointer gestures, tablets, touch** (`crate::devices`, DRM backend): libinput swipe/pinch/hold, touch and tablet-tool events are forwarded through Smithay's seat and tablet handles (anvil's `input_handler.rs` pattern); a touch or pen-down focuses the window under it. ## XWayland progress

**XWayland is implemented and live-verified in the VM** (`crate::xwayland`, `crate::focus`). X11 programs run inside the compositor and `bspc` treats their windows like any other — bspwm *is* an X11 window manager, so `WM_CLASS` class and instance reach `bspc rule` as bspwm gives them.
- **Lazy start.** Smithay's `XWayland::spawn` starts `Xwayland` immediately. It is pointed at a shim instead: `PATH` gets a directory first whose `Xwayland` is a symlink to `bspwm-rs` itself; run under that name `main` calls `xwayland::run_shim_if_invoked`, which `poll(2)`s the inherited `-listenfd` sockets and, at the first X11 connection, `exec`s the real `Xwayland` with the same arguments and descriptors (socket activation). `DISPLAY=:<N>` is exported before `bspwmrc`. After it has started, `Xwayland` stays until the compositor exits (its own `-terminate` would fire at the last client, but the window manager's X connection counts as one). Live: before any X11 client the only `Xwayland` process was the shim; after `xterm` connected the real server ran and the shim was gone.
- **Window management.** A managed X11 window (`map_window_request`) goes through the same `shell::map_new_window` as an `xdg_toplevel` (refactored out of `map_new_toplevel`): rules, tiling, focus, borders, `bspc node`. Live: `bspc rule -a TestClass state=floating` matched an `xterm -class TestClass -name testinst` and `query -T` reported class `TestClass`, instance `testinst`, state `floating`; without a rule it tiled to the full slot; `bspc node -c` closed it. Override-redirect windows and menu/tooltip/notification/popup types are placed where the program asked and stay outside the tree (bspwm never manages override-redirect windows); they are re-raised after every reconcile so tiling cannot bury a menu — **untested with a real menu**. A fullscreen request from an X11 window becomes `bspc node -t fullscreen`. `configure_request` from a managed window is answered with the tree's rectangle. Title/class changes reach taskbars and `bspc` queries.
- **Keyboard focus.** The seat's `KeyboardFocus` is now `focus::FocusTarget { Surface, X11 }`: focus on the `wl_surface` alone only tells Xwayland which surface is focused, the X server also needs `XSetInputFocus`, which Smithay does in `X11Surface`'s `KeyboardTarget::enter`. Found by the live test (typing did nothing until this). Live: keys sent through the QEMU monitor arrived in an `xterm` (`got:hi`). `surface_associated` completes focus meant for a window whose `wl_surface` did not exist yet at map time.
- **Clipboard.** Selections are bridged both ways (`SelectionHandler` ↔ `XwmHandler`). Live: a Wayland primary selection (`wl-copy --primary`) was pasted into `xterm` with Shift+Insert. X→Wayland was tested later with `examples/x11_probe.rs`: a client owning `CLIPBOARD` was pasted by `wl-paste`, and `wl-copy` text was pasted by the probe (`paste`).
- **Hard-rule note:** `XwmHandler::xwm_state` must return `&mut X11Wm` unconditionally, so it can only panic if called with no X window manager (Smithay calls it only from the WM's own event source); documented in the module.
- **Window types and struts** (`xwayland::{type_defaults, read_extra, apply_struts}`, ported from bspwm's `src/rule.c` `apply_rules()` and `src/ewmh.c` `ewmh_handle_struts()`): dialogs float centred, toolbars/utility windows are not focused, docks/desktops/notifications are not managed (rules override); an X11 window's floating rectangle now starts from its own geometry (bspwm's `initialize_floating_rectangle()`), and `center` rules work for every window. A window's `_NET_WM_STRUT_PARTIAL` grows the padding of the monitors it touches (`bsp_core::wm::Wm::apply_ewmh_struts`) unless `bspc config ignore_ewmh_struts` is on; like bspwm nothing gives the space back. Smithay does not offer properties it does not know, so `_NET_WM_STRUT_PARTIAL` and the dock/desktop types are read over a short-lived second X connection when the window maps (a strut set later is not seen). **Live**: a dialog mapped floating at exactly `(490,300)` 300×200 on a 1280×800 monitor, a toolbar did not take focus, a dock with a 30 px strut was not a node and made `top_padding` 30 (the tiled window moved from y 6 to y 36), and `ignore_ewmh_struts true` made a second dock change nothing.
- **Lazy stop** (`xwayland::schedule_idle_stop`): 30 s after the last X11 window is gone, with no other X11 client connected (counted through the X Resource extension by client pid, `xwayland::foreign_x_clients`: Firefox holds a windowless X connection during WebRTC screen sharing and crashed with an XIO error when `Xwayland` was stopped under it; the check is re-armed while any is connected) and none owning a selection, `Xwayland` is stopped (its memory returned) and a fresh dormant shim takes its place; the old process holds the display for a moment, so the respawn retries. **Live**: the process became the shim, and the next X11 client started the real server again; also with a clipboard owner that had exited. An X11 client that connected but shows no window and owns no selection is not noticed.
- Not done: `_NET_ACTIVE_WINDOW` *requests* from X11 clients (`wmctrl -a`; Smithay's X11 window manager does not pass them on — the root property itself is kept current by Smithay), the `wm_state`/maximize/minimize requests, struts set after the window mapped, HiDPI scaling of X11 windows.

## Hardware backend progress

**Hybrid GPUs are implemented; they are verified only on two software-rendered virtual GPUs, not real dual-GPU hardware.** How it works (`udev_backend::renderer_for`): every GPU is keyed by its *render node* (`render_node_of`; udev reports card nodes and the same GPU must not compare unequal to itself). An output on the primary (boot) GPU renders directly on it. An output on any other GPU is composited on the primary — where clients' buffers live — into an offscreen buffer that `GpuManager::renderer(primary, target, format)` copies into the secondary's scanout buffer, as anvil does. A secondary GPU's scanout formats are the intersection of its own and the primary's render formats. If the copy route cannot be built (a GPU missing from the manager, no common dmabuf format) or fails while rendering, that output falls back to rendering on its own GPU alone (`SurfaceData::copy_route_failed`; shm clients keep working, a dmabuf client living on the other GPU may not show). `Backend::early_import` (called after every commit, only with 2+ GPUs) imports a committed buffer on the primary right away so the cross-GPU copy is not paid inside the frame. The primary GPU is set up first (a two-GPU VM listed the secondary first, which made its setup fall back).

**Debugging it on real hardware** — run with `BSPWM_LOG=debug` (add `bspwm_rs::udev_backend=trace` for a line per frame). What to look for:
- `GPUs on this seat boot_gpu=… all_gpus=…` and `primary GPU chosen … why=…` — did it pick the GPU you expect? If the wrong one, the firmware's boot GPU differs from what drives your monitors.
- `GPU added node=… render_node=… is_primary=…` and `secondary GPU render formats intersected … primary=N own=M common=K` — `common=0` (also a WARN) means no dmabuf format is shared and the copy route cannot work.
- `initializing a connector … hybrid=true|false` — which route each output takes. `render route: primary GPU + copy to target` (trace) means the copy route is live; `cannot render on the primary GPU and copy (reason); falling back …` names why it is not.
- `multi-GPU copy route failed (…); this output now renders on its own GPU only` (WARN) — the copy failed at render time.
- WARN `Error importing dmabuf from … to …` from `smithay::backend::renderer::multigpu` (with EGL `BAD_ALLOC` errors) — the direct GPU-to-GPU dmabuf import failed and Smithay fell back to copying through system memory: correct output but slower. Seen on the VM's software GPUs; on real hardware it usually means a modifier/format mismatch or a driver that cannot import the other's buffers.
- `udev: DRM device added|changed|removed`, `DRM device removed; dropping its outputs and its renderer` — hotplug flow; `early import … failed` (debug) — a client buffer that could not be pre-imported.
Also in the VM tests: a GPU hot-remove/re-add (unbinding and rebinding the virtio-gpu driver) removes its outputs and re-creates them — this found and fixed a bug (a removed device's node cannot be looked up in sysfs, so removal was silently ignored; it is now matched by device number), plus render nodes being reported as devices to open. Verified with a virgl GPU (`-device virtio-gpu-gl-pci`, `-display egl-headless`): three client dmabufs imported and none refused, and an EGL client drew at ~630 FPS. Not verified: connector-level hotplug (monitor plug/unplug) — QEMU cannot simulate it; the code path (`device_changed` → `DrmScanner`) is exercised at startup only.

**Robustness pass (investigating every failure seen so far), live-verified in the VM.** Findings and fixes:
- **calloop "Failed to unregister source (EBADF)" on every `bspc` call** — real bug, `ipc::reply_and_close` took the connection out of its slot and dropped it (closing the fd) *before* returning `PostAction::Remove`, so calloop then tried to deregister an already-closed fd. It now sends the reply and leaves the connection in place; dropping the source closes it after deregistration. 0 warnings afterwards.
- **`unwrap()`/`expect()` on runtime paths (hard rule 3), 20+ sites** across `input`, `pointer_action`, `shell`, `hotkeys`, `state`, `ipc`, `udev_backend` and `winit_backend`'s startup — each now returns/logs instead of panicking (missing keyboard, unreadable toplevel data, poisoned xkb mutex, missing client, failed event-source registration, `unreachable!()` in the winit render error mapping). `ClientState` lookup falls back to a shared default.
- **Idle polling** — the DRM render loop rescheduled itself every 16 ms whenever a frame was empty, i.e. forever on a static screen (against the performance budget, and pointless wakeups). Rendering is now demand-driven: `Backend::queue_redraw` (called on client commit, cursor change, toplevel destroy, every IPC command and every libinput event) marks surfaces dirty; the main loop's `render_dirty` renders each dirty surface with no frame in flight; a queued frame's vblank (`frame_finish`) only clears its pending flag. Frame callbacks are now also sent for empty frames (a client that committed without visible damage still waits on one). Live: 2 frames at startup then zero while idle; an animating client is rendered continuously; zero after it closes.
- **Stale `wayland-N` after a kill** — the process ignored `SIGTERM`, so no `Drop` removed its sockets and the next start took `wayland-N+1`. `state::init_quit_signals` makes `SIGINT`/`SIGHUP`/`SIGTERM` stop the main loop (as bspwm's `sig_handler()` does); sockets are gone after `kill`.
- **Startup segfault** while draining libinput's initial events (found while fixing device registration): dropping each event while iterating the context crashed; devices are now collected first, then handled.
- **Partly drawn static frames (stair-stepped fill in QEMU's `screendump`)** — fixed: `render_surface` did not honor `RenderFrameResult::needs_sync()` (Smithay's docs make this the caller's job, and anvil waits on the primary element's `SyncPoint`), so a frame could be scanned out before its render finished, and a static screen never re-flushed it. It now waits before `queue_frame`. Before: most static screenshots partial; after: 7 consecutive screenshots of a freshly started compositor were complete and stable. (Smithay's GLES renderer already `glFinish`es when it has no fence, so the exact mechanism is not proven, but the symptom is gone.)
- **Left as they are, with reasons:** `Failed to restore previous state: Invalid argument` and `Failed to drop drm master state: Invalid argument` at exit — Smithay's own DRM-device drop code (`device/atomic.rs`, `device/fd.rs`); the restore replays the console's saved KMS properties, including the mode blob Smithay itself destroys at the first modeset (the `Failed to destroy old mode property blob` warning), and the master drop fails because the seat manager (libseat/logind) owns master. Cosmetic: the text console returns. Fixing it means patching or forking Smithay, which is out of scope. `failed to create signaled syncobj` — virtio-gpu has no syncobj; Smithay falls back. Shader-cache and `bspwmrc` `Permission denied` — the test chroot's read-only host root, not the compositor.

**`linux-dmabuf` (dmabuf import) is implemented on the DRM backend; the global is live-verified, the import path is not.** `State` carries a `DmabufState` and implements `DmabufHandler` (generic over the backend; `delegate_dmabuf!`): a client's dmabuf is handed to the new `Backend::dmabuf_imported`, whose default refuses (the nested backend does not advertise the global, so its clients keep using `wl_shm`). `udev_backend::run` creates the `zwp_linux_dmabuf_v1` v4 global after the initial device scan, with the primary GPU's renderer formats and its render node as the feedback's main device; `DrmData::dmabuf_imported` imports the buffer into that renderer (`ImportDma::import_dmabuf`) and refuses on error. Live result in the VM: `linux-dmabuf enabled` was logged, and — the first real client on the DRM backend — an EGL client (`es2gears_wayland`) connected, was tiled (`bspc query -N` listed it), drawn with its border, and its animated gears were visible in a screendump. Not confirmed: that its buffers actually went through the dmabuf path — Mesa in the chroot failed to open a DRI device ("failed to get driver name for fd -1"), so it most likely fell back to `wl_shm`. Multi-GPU copy paths (buffers from a non-primary GPU) are still not handled. The screendump partial-update artifacts noted above are consistent with software (llvmpipe) rendering being slow in the VM's debug build.

**Cursor drawing is implemented and live-verified in the VM.** The DRM backend owns the screen, so nothing else draws the pointer: `crate::cursor` loads the default cursor from the xcursor theme (`XCURSOR_THEME`, else `default`; `XCURSOR_SIZE`, else 24; a plain square if no theme is found) into a `MemoryRenderBuffer`, or renders the client surface from `wl_pointer.set_cursor` (`CursorImageStatus::Surface`, with its hotspot); `Hidden` draws nothing. `render::output_elements` takes the cursor elements as a new argument and puts them first (topmost); the winit backend passes none, since its host compositor draws the pointer. No cursor animation (first frame only). In the VM (virtio mouse), a screendump through the QEMU monitor showed the theme's arrow at the pointer, and it moved with relative motion. Two related findings from that test: (1) libinput queues its initial "device added" events on a first `dispatch()` and its fd is not readable until then, so `run()` now drains them itself before handing the context to calloop — otherwise keyboard LEDs and the `bspc input` device list stayed empty until the first real input event; pointer acceleration then round-tripped (`bspc input <mouse> -a 0.5`). (2) QEMU's `screendump` on virtio-gpu sometimes showed only part of the frame updated (the top of the screen the compositor background, the rest not yet flushed); the cursor and the rest of the pipeline were fine, and this was not investigated further.

**Stage E (`bspc output`/`bspc input`) is implemented and live-verified in the VM.** `bsp_ipc::exec` only has `&mut Wm`, the registry and the `Adapter` — no `Output`, DRM device or libinput handle — so `crate::hardware::HwModel` (inside `WindowAdapter`, kept current by the DRM backend on connector/device hotplug) holds a plain-data model, validates each request synchronously (unknown output/device, no such mode — a requested `@60` matches the nearest real refresh within 0.5 Hz, e.g. 59.94 —, non-positive scale, negative repeat, accel outside −1..1, repeat on a non-keyboard, accel on `keyboard`) and queues it. `ipc::execute_and_broadcast` then calls `apply_hardware_changes`: `-m` goes through the new `Backend::set_output_mode` (DRM: `DrmOutput::use_mode` on the connector's own mode list), `-s` and `-p` change the Smithay `Output`'s scale/position and re-map it in the `Space`, then the matching `bsp-core` monitor gets the output's new logical geometry via `bsp_ipc::exec::set_monitor_rectangle` (the same path as `bspc monitor -g`, including `reorder_monitor`, re-arranging and a `MonitorGeometry` event). `bspc input keyboard -r RATE DELAY` calls the seat keyboard's `change_repeat_info`; `bspc input <pointer> -a FACTOR` calls libinput's `config_accel_set_speed` through `Backend::set_pointer_accel`. Input device names are `keyboard` (the virtual seat keyboard) plus each libinput pointer device. **Live result** (two `Virtual-*` connectors): `bspc output` listed both, `output Virtual-1` reported mode/scale/position/modes, `-m 1024x768@60` succeeded and a nonexistent mode failed with a proper message, `-s 2 -p 100 50` gave the monitor rectangle `x=100 y=50 512x384` (1024×768 at scale 2), `input keyboard -r 40 250` round-tripped. Pointer accel and hotplug-time input listing could not be exercised: the VM has no pointing device. On the nested backend there are no outputs in the model, so `bspc output` lists nothing there. Log observation (pre-existing, not from this stage): each `bspc` connection produces a benign calloop "Failed to unregister source (EBADF)" warning when its socket closes.

**Stage D (VT switching) is implemented and live-verified in the VM.** `input::vt_switch_target` classifies a `Ctrl+Alt+F<n>` press (accepting both `F1`–`F12` and `XF86Switch_VT_1`–`12` keysyms); the DRM keyboard filter calls `Session::change_vt(n)` and swallows the key, checked after the emergency quit key and before `hotkeys::filter`. `ctrl-alt-f2` sent through the QEMU monitor switched the guest to tty2 (session paused); `ctrl-alt-f1` switched back (session resumed, frames queued again). The live test found a bug: while paused, `render_surface` rescheduled itself every 16 ms logging "device is currently paused"; it now returns early when the session is inactive (resume re-kicks rendering).

**Stage C (DRM/KMS backend) is implemented and live-verified in the QEMU VM** (`crate::udev_backend`, cargo feature `real`). `State` is now generic, `State<Bd: Backend + 'static>`, following Smithay's reference compositor anvil: the `Backend` trait (`seat_name`, `reset_buffers`, `early_import`, `update_led_state`, `HAS_RELATIVE_MOTION`, `HAS_GESTURES`) is implemented by `WinitData` (nested) and `DrmData` (real); every handler and helper is generic over it. `DrmData` holds the libseat session, primary GPU, a `GpuManager<GbmGlesBackend<..>>`, and per-device state (`DrmOutputManager`, `DrmScanner`, per-CRTC surfaces). Flow: `device_added` (session open, `DrmDevice`, `GbmDevice`, `EGLDisplay`, render node, allocator/exporter, `DrmOutputManager`) → `device_changed` (`DrmScanner` diff) → `connector_connected` (output named `<interface>-<id>`, e.g. `Virtual-1`, preferred mode, left-to-right placement, a matching `bsp-core` `Monitor` via `Wm::add_monitor`, `initialize_output`) / `connector_disconnected`. **Stage B (session + udev device enumeration) is implemented and live-verified** (`crate::udev_backend`, `docs/design.md` roadmap: the hardware backend, "Started"). ## Known issues

- **A client's own content can render vertically flipped on the nested (winit) backend with the NVIDIA proprietary driver.** Found live testing with `alacritty` (user report, confirmed by screenshotting the actual nested window rather than trusting logs alone): the nested window's own chrome and this crate's own border strips (`render.rs`, plain solid-color quads, not texture-sampled) render in the correct position, but `alacritty`'s terminal content is upside down with its left-to-right character order preserved — a pure vertical flip, not a full 180° rotation. `alacritty`'s own stderr shows Mesa's EGL loader failing to find a DRM device to accelerate against (`MESA-EGL: warning: failed to get driver name for fd -1`), meaning it falls back to a software-rendered, `wl_shm`-presented path; Smithay's own `wl_shm` import (`ImportMemWl::import_shm_buffer`) hardcodes `y_inverted: false` and is used, unmodified, by every other Smithay-based compositor without this problem, so the flip is not something this crate's code controls — it happens inside that Mesa software/`wl_shm` fallback conversion itself. Tried and reverted: calling `ImportEgl::bind_wl_display` (`crates/bsp-compositor/src/winit_backend.rs`'s history) to give clients a real `wl_drm` GPU path instead of that fallback — this made `alacritty` fail to start entirely (`Context` error, raw code 12828) rather than fixing the flip, pointing to a further NVIDIA/Mesa client-vs-NVIDIA-only-compositor EGL interop gap. Since the nested winit backend is explicitly a development-only tool excluded from release builds (`docs/design.md`, Performance budget), and the real target (the hardware backend's DRM/KMS backend) uses a wholly different, GBM-based buffer import path unrelated to this nested-Wayland-specific interaction, this is logged as a known development-environment limitation rather than chased further for now.

## Border rendering

Border colors come from `bspc config normal_border_color`/`active_border_color`/`focused_border_color` (`Wm::settings`). A desktop's focused node is drawn with `focused_border_color` on the focused monitor and `active_border_color` on any other, everything else with `normal_border_color` (`src/window.c` `get_border_color()`). A change is picked up on the next frame. **Live**: a window set to red (focused) and two to blue (normal) rendered as such, and the colors changed in a running session. `presel_feedback_color` is stored but the preselection feedback is not drawn.

A node's border is four separate solid-color strips (top/bottom/left/right) framing its `tiled_rectangle`, not one rectangle drawn behind the surface: `smithay::desktop::space::render_output`'s `custom_elements` argument always draws on top of window content (elements earlier in its internal render list are topmost, and there is no ready-made way to interleave a custom element behind one specific window's surface without writing a full custom combining `RenderElement` — see `render.rs`'s module doc comment). Four non-overlapping strips sidestep the ordering problem entirely rather than fighting it. Colors are hardcoded (`FOCUSED_BORDER_COLOR`/`NORMAL_BORDER_COLOR`) since `bsp-core::Settings` has no color fields yet (colors are an X11/pointer-adjacent concern, `docs/bsp-core.md`).

## Renderer abstraction

Decision: drawing code never names a concrete renderer, so OpenGL ES, Vulkan and Pixman are interchangeable and chosen at runtime. **Not yet implemented**: `render.rs` currently names `GlesRenderer` concretely (the nested compositor only needed one working renderer to prove the pipeline); making it generic over Smithay's renderer traits, and choosing among GLES/Pixman/Vulkan at runtime, is deferred to when a second renderer actually exists to switch to (real hardware without working GLES, the hardware backend).

- **Selection** (planned): `BSPWM_RENDERER=gles|vulkan|pixman`. Default order is OpenGL ES, then Pixman if GL setup fails.
- **Vulkan**: opt-in until Smithay's Vulkan rendering support is complete enough for daily use; its status is checked before the hardware backend.
- **Cargo features**: `renderer-gles` (default, in use), `renderer-pixman` (declared on the `smithay` dependency, not yet used by `render.rs`), `renderer-vulkan` (not yet declared).
- **Testing**: CI builds every feature combination. Pixman needs no GPU, so rendering is tested headlessly against reference images, and GPU renderers are checked on real hardware. Not implemented yet — no CI workflow exists for this crate (only `bsp-core`'s dependency-isolation check runs today, `.github/workflows/ci.yml`).

| Renderer | Role | Needs |
| --- | --- | --- |
| OpenGL ES | Default, in use | Mesa or NVIDIA 555+ |
| Vulkan | Optional, opt-in | Vulkan driver; Smithay support to be verified |
| Pixman | Fallback, CI tests | CPU only — declared as a `smithay` feature, not wired into `render.rs` yet |

## Focus history

`state.wm.sync_history()` runs once per event-loop turn in both backends (next to `extras::arm_commit_timers`); `bsp_ipc::exec::execute` also runs it around every command, which covers hotkeys' inline `bspc` calls. **Live in the VM** with three windows: `node -f last` went back and forth between the two most recent, `node -f older` stepped past the current one, with `wm -h off` `older`/`newer` walked through the history, `desktop -f last` and the Alt+Tab hotkey (`super + Tab`, `desktop -f last`) returned to the previous desktop, and `wm -d` listed the entries.

## Closing and opening windows

`shell::unmap_window` reports `node_remove`, removes the node, and refocuses through `bsp_ipc::exec::focus_node`/`activate_node` (closing the focused window hands focus to the window focused before it, with the `node_focus` event bspwm sends; a window whose node was already removed, as after `node -k`, still leaves the space and the adapter), re-arranges, and calls `sync_wayland_from_core` so the remaining windows grow into the freed space and keyboard focus follows. `map_new_window` ends with the same sync so the siblings of a new window shrink at once. **Live in the VM**: with three windows, closing the middle one re-tiled the other two 50/50; closing the focused one moved focus to the previous window and `super + h`/`l` switched between the rest. A freeze of mouse and keyboard reported on real hardware after closing a window and switching back and forth was **not reproduced** in the VM.

A layer surface (rofi) that holds the keyboard and is then destroyed hands it back: `layers::layer_destroyed` clears the focus and calls `input::sync_keyboard_focus`, which also ignores a focused surface that is no longer alive. **Live**: with a window open, rofi took the keyboard and on exit the log showed `keyboard focus follows the focused node` at once.

**Popups and panel focus.** `shell::on_commit` sends an `xdg_popup` its initial configure (without it clients never map menus and tooltips). `sync_keyboard_focus` lets only an exclusive layer surface keep the keyboard; an `on_demand` panel focused by a click (waybar) gives it back to the tree's focus on the next change. Spawned commands are reaped by a helper thread (`hotkeys::reap`). On `PauseSession` each output is cleared before the device is paused, so the next session finds no plane of ours enabled.

**Closing focus, popup placement, stray Xwayland.** `unmap_window` releases keyboard focus held by the closing window before unmapping it, so the tree's next window takes it at once. `shell::unconstrain_popup` keeps popups inside their output (flip/slide/resize as the client asked). The lazy Xwayland shim requests `SIGKILL` on parent death (`SIGTERM` is blocked in children by the compositor's signal handling), so no `Xwayland` outlives the compositor.

**Popup grabs and desktop focus.** A popup that calls `xdg_popup.grab` is remembered and dismissed by the next button press outside its tree. Keyboard focus follows the tree's focus when desktops change, because only an exclusive layer surface is exempt from `sync_keyboard_focus`. `State::switch_vt` runs before `change_vt`: it commits one last frame per output with every element composited on the primary plane (`FrameFlags::empty()`, `commit_frame`), which turns our other planes off (falling back to `DrmData::clear_planes`), and stops drawing until the resume (the CRTC stays on, so the monitor keeps its signal and the next session needs no full modeset); at `PauseSession` the kernel has already revoked DRM master, so a clear there fails. The resume uses `DrmOutputManager::activate`, which resets the outputs' plane state.

**Fullscreen, signals, gamma.** `xdg_toplevel` fullscreen requests become `bspc node -t fullscreen`; a fullscreen window covers the monitor and the top layer is drawn beneath it. Spawned processes get an empty signal mask (`spawn`). Each output remembers its last gamma ramp and writes it again after the first frame following a resume.

**VT switching and input.** On `PauseSession` the DRM outputs are paused and libinput is suspended; on `ActivateSession` libinput is resumed (its devices are re-added and reported again) and the outputs are reactivated. Without the libinput calls every input device stayed closed after coming back to the session. **Live**: `chvt 2; chvt 1` in the VM, then a hotkey switched desktops. **Logging**: `BSPWM_LOG=debug` also enables every renderer and frame message (about 15 MB a minute with a screen-capture client); `BSPWM_LOG=info,bspwm_rs=debug` keeps only this crate's.

`shell::window_size_limits` reads a window's min/max size (xdg cached state or X11 hints); `shell::refresh_size_constraints` sets the leaf's tree constraints from the minimum (at map and on commit, then re-arranges) and `sync_one_window` applies `honor_size_hints` by clamping the rectangle.
